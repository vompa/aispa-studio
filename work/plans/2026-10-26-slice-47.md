## Stand im Code (gemessen am 26.10.2026, `dev` auf `24bf91c`)
- `/buchen/` wird an drei Stellen ausgeliefert: nginx im Server-Betrieb (`docker/nginx.conf`, `location /buchen/`), die API im Einzelplatz mit `Hosting:WebRoot` (`src/AispaStudio.Api/System/TeamWebRoot.cs`: `UseDefaultFiles`/`UseStaticFiles` für `/buchen/`, `MapFallback` für tiefere Pfade) und Vite in der Entwicklung.
- Kein Header und kein `<meta http-equiv>` setzt heute eine CSP (Suche nach „Content-Security-Policy“ ohne Treffer).
- Bezahlung (Anzahlung, Kartengarantie, Gutschein) läuft ausschließlich per Weiterleitung zu Stripe Checkout (`paymentUrl`, `window.location.assign`, `<a href>`); der Kundenbereich lädt kein Stripe.js, keinen Stripe-Frame und ruft `api.stripe.com` nicht aus dem Browser auf. Alle `fetch`-Aufrufe gehen an `/api` derselben Herkunft. Externe Ziele sind nur Links in neuem Tab (Karten-Route).
- Formulare senden per `onSubmit` mit `fetch`, kein Formular-Post an fremde Ziele.

## Annahmen (bei Freigabe bestätigen)
1. **Richtlinie:** `default-src 'self'; base-uri 'self'; object-src 'none'; form-action 'self'` plus `img-src 'self' data:` nur, falls der Build Bilder als `data:`-URL einbettet (wird am Build gemessen, sonst entfällt es). Empfehlung: ja.
2. **Stripe gezielt = keine Stripe-Quelle freigeben:** Stripe Checkout ist eine Seitennavigation, die keine CSP-Direktive erfasst. Freigaben ohne Nutzung widersprechen dem Grundsatz „so eng wie möglich“. Der ADR nennt die Quellen für den Fall, dass später Stripe.js/Elements kommt (`script-src https://js.stripe.com`, `frame-src https://js.stripe.com https://hooks.stripe.com`, `connect-src https://api.stripe.com`). Empfehlung: ja.
3. **Eine Quelle für die Richtlinie:** Konstante in der API (`BookingContentSecurityPolicy`); `docker/nginx.conf` trägt denselben Text, ein Test vergleicht beide. Empfehlung: ja.
4. **Nur Bericht in der Konsole, kein `report-to`-Endpunkt:** ein Meldeendpunkt wäre neue API-Fläche (Missbrauch, Speicherung); der ADR beschreibt ihn als möglichen Schritt vor dem Umschalten. Empfehlung: ja.
5. **Keine CSP in der Entwicklung (Vite):** der Dev-Server spritzt Inline-Skripte (React-Refresh) ein und würde nur Rauschen erzeugen; maßgeblich sind die gebauten Auslieferungen. Empfehlung: ja.
6. **`frame-ancestors` bleibt offen:** ob Spas den Kundenbereich auf ihrer Website einbetten dürfen, ist nicht entschieden; der ADR führt es als offenen Punkt für den Auftraggeber. Empfehlung: ja.
7. **Umschalten auf durchsetzend:** ein Schritt – Header-Name in der Konstanten und in `nginx.conf` von `Content-Security-Policy-Report-Only` auf `Content-Security-Policy`, nachdem ein Release ohne Meldungen lief; steht im ADR. Kein Konfigurationsschalter (nichts auf Vorrat). Empfehlung: ja.

## Review-Fokus
- Naht `TeamWebRoot` (Einzelplatz): der Test fängt einen fehlenden Header auf `/buchen/` (DefaultFiles-Pfad) und auf `/buchen/<tiefer Pfad>` (Fallback) sowie einen Header auf der Team-Oberfläche `/`; er fängt nicht, ob der Browser die Richtlinie ohne Meldung durchlässt.
- Naht `docker/nginx.conf`: der Test fängt abweichenden Richtlinientext und fehlendes `always`; er fängt nicht, ob nginx die Datei so lädt (Prüfung per Browser gegen die gebaute Seite).
- Browserprüfung (Skript mit `playwright-core` im Scratchpad): fängt echte Verstöße des gebauten Kundenbereichs bis zur Bezahl-Weiterleitung; im Repository bleibt kein Browser-Test (keine CI-Infrastruktur dafür).
