# Konventionen – aispa-studio
> Verweise, keine Kopien. Jede Angabe hat einen Eigentümer: das Dokument hinter dem Pfeil.

- Integrationsbranch: `dev` im Hauptordner; nach `main` nur gesammelt per Merge-Commit über den Entwurfs-PR `dev` → `main`, wenn der Auftraggeber einen Stand ausprobiert hat und die CI grün ist ← docs/entscheidungen/0060-weiterarbeit-auf-einem-branch-dev.md, CLAUDE.md „Arbeitsweise“
- Slice-Branch: `slice-NN`, abgezweigt von `dev` ← Skill vibe-coding (neu für dieses Repository)
- Merge-Stil: ein Squash-Commit je Slice auf `dev`; nie pushen, Push und Merge nach `main` nur mit Freigabe vom Auftraggeber ← Auftrag Runde R01; Freigaberegel: CLAUDE.md „Arbeitsweise“, docs/arbeitsweise.md §2 (siehe Konflikte)
- Commit-Sprache und Stil: Deutsch, Betreff im Aktiv ohne Punkt, ohne Präfix wie `feat:`, Befund-Kennungen in Klammern am Ende (z. B. „(Ä69, Ä70)“, „(T-010, ADR 0079)“), Rumpf nennt das Warum ← docs/arbeitsweise.md §2 Schritt 4 und §4, git log
- Build: `dotnet build AispaStudio.slnx -c Release` (Warnungen sind Fehler; schreibt `web/openapi/aispa-api.json`) ← CLAUDE.md „Befehle“, docs/arbeitsweise.md §3
- Test: API `dotnet test --project tests/AispaStudio.Api.Tests -c Release` (Docker für Testcontainers); Windows-App `dotnet test --project tests/AispaStudio.Desktop.Tests -c Release`; Web `cd web && npx vitest run --maxWorkers=3` ← CLAUDE.md „Befehle“, docs/arbeitsweise.md §3; `--maxWorkers=3` und „Web-Tests nur ohne laufenden AppHost“ aus den Fallen der Sitzungen (CLAUDE.md „Bekannte Fallen“ nennt sie nicht)
- Lint / Formatprüfung: `dotnet format AispaStudio.slnx --verify-no-changes`; Web `cd web && npm run lint && npm run typecheck` ← CLAUDE.md „Befehle“, .github/workflows/ci.yml
- Baseline check (Basisprüfung, vor jeder Slice; der englische Schlüssel am Zeilenanfang ist Pflicht, die Merge-Warteschlange verlangt jeden Befehl dieser Zeile im Prüfnachweis): `dotnet format AispaStudio.slnx --verify-no-changes` und `dotnet build AispaStudio.slnx -c Release` ← abgeleitet aus .github/workflows/ci.yml (Job „Backend“, erste Schritte) [Annahme: die vollen Testläufe dauern zu lange für jede Slice]
- Prüfungen für eine Slice: Basisprüfung; bei Änderungen an der Windows-App in drei Stufen – (1) nur eine Ansicht betroffen (Dateien unter einem View, seinem ViewModel und dessen Tests): die Testklassen dieser Ansicht `dotnet test --project tests/AispaStudio.Desktop.Tests -c Release --filter-class "AispaStudio.Desktop.Tests.<Klasse>"` (mehrere `--filter-class` sind ODER-verknüpft) und in einem zweiten Aufruf die Scan-Tests über alle Seiten `dotnet test --project tests/AispaStudio.Desktop.Tests -c Release --no-build --filter-method "*jeder_Seite*" --filter-method "*Jede_Ansicht*" --filter-method "*Jede_Seite*" --filter-method "*melden_keine_Bindungsfehler"` sowie `--filter-class "AispaStudio.Desktop.Tests.DesignTokenTests" --filter-class "AispaStudio.Desktop.Tests.GridValueTests"` (GridValueTests seit R05: Slice 95 setzte einen Abstand gegen den Brief, erst in der vollen Suite von Slice 96 rot) (Klassen- und Methodenfilter in einem Aufruf sind UND-verknüpft, deshalb getrennt; neue Scan-Tests heißen `…jeder_Seite…`, `Jede_Ansicht…` oder `Jede_Seite…`, damit der Filter sie findet); bei Änderungen an Tastenkürzeln, Fokus oder Tab-Reihenfolge zusätzlich die Fokus- und Tab-Tests `dotnet test --project tests/AispaStudio.Desktop.Tests -c Release --no-build --filter-method "*Fokusreihenfolge*" --filter-method "*Tab*"` (R03: Slice 75 brach `Fokusreihenfolge_Termin_Panel`, erst auf `dev` rot); (2) Gemeinsames betroffen (`Controls/`, `Styles.axaml`, `Colors.axaml`, `MainWindow`, Shell, ein ViewModel mit mehreren Nutzern): volle Desktop-Suite `dotnet test --project tests/AispaStudio.Desktop.Tests -c Release`; (3) Rundenabschluss: volle Prüfkette (unten); bei Änderungen am Web `cd web && npm run lint && npm run typecheck && npx vitest run --maxWorkers=3 <betroffene Testdateien> && npm run build && npm run check:bundle` (die ganze Web-Suite nur in der vollen Prüfkette, User, 01.11.2026); bei Änderungen an der API zusätzlich die API-Tests und `cd web && npm run gen:api` (beide erzeugten Dateien committen); eine neue Regel an einem Endpunkt, Service oder einer Basisklasse (etwa „keine Buchung in der Vergangenheit“): alle Aufrufer per Suche finden und ihre Tests laufen lassen, sonst die ganze API-Suite `dotnet test --project tests/AispaStudio.Api.Tests -c Release` vor „grün“ (R03: `BusinessReportTests` erst nach dem Rundenabschluss rot) ← docs/arbeitsweise.md §3, CLAUDE.md „Regeln im Code“; Stufen für die Windows-App: Auftraggeber, 25.10.2026 (Slice 34: volle Suite unter Last 22 min statt 10)
- Nie zwei volle Desktop-Suiten zugleich: vor einem vollen Lauf (Desktop-Suite, `dotnet test --solution`, volle Prüfkette) die Sperre `.slice-loop/full-suite.lock/` im Hauptordner nehmen und danach freigeben, wie `.claude/commands/slice.md` Abschnitt 4 Schritt 1 es beschreibt; parallele Suiten verdoppeln die Laufzeit und machen sich gegenseitig rot ← Auftraggeber, 25.10.2026; vibe-coding 1.2.0 (Sperre); CLAUDE.md „Bekannte Fallen“ (Vitest unter Last)
- Testgruppen (Messung 01.11.2026: API 14 min, Desktop 50 min, davon `ViewTests` 3.014 s und alle übrigen Desktop-Tests 158 s): schnell sind die Desktop-Tests ohne `ViewTests` `dotnet test --project tests/AispaStudio.Desktop.Tests -c Release --filter-not-class "AispaStudio.Desktop.Tests.ViewTests"` (rund 2,5 min); `ViewTests` in der Slice nur für die geänderte Ansicht per `--filter-method`, alle zusammen nach dem Bauen mit `pwsh scripts/view-tests.ps1` in vier Prozessen (rund 13 min statt über 50; in einem Prozess geht nicht parallel, er hat nur einen Oberflächen-Thread); die Seitenscans sowie die API-Klassen `DemoBulkTests`, `StartupStateTests` und `DemoSeederTests` nur im Meilenstein und beim Rundenabschluss, in der Slice nur, wenn sie die Beispieldaten oder den Start ändert ← User, 01.11.2026
- Parallele Slices: `/slice NN parallel` endet mit `SLICE-READY: NN` statt eigenem Squash, nachdem die Sitzung den Spitzen-SHA in `.slice-loop/slice-NN.ready` geschrieben hat; die Warteschlange squasht im Hauptordner mit `python .claude/scripts/slice_loop.py --merge`, mit `--merge --verify` (volle Prüfkette auf `dev`) so oft, wie die Prüfstufe verlangt, nur Slices, deren Ready-Datei die Spitze nennt; Konflikte, bei denen beide Seiten nur anhängen (PR-Protokoll, Befundliste), die Status-Zeile der Runde, `work/checklist.md` und die Rundenakte löst sie selbst, jeder andere Konflikt lässt die Slice mit ihrem Branch liegen und wird in der Slice-Sitzung gelöst; höchstens zwei Slices zugleich (Auftraggeber, 30.10.2026: drei Sitzungen auf einem Rechner machten unbeteiligte Tests unter Last rot und reihten sich an der Sperre an), Slices mit gemeinsamen Dateien (Feld `files` in `work/_slices.json`) nacheinander ← vibe-coding 1.2.0 bis 1.5.0
- Check level (Prüfstufe: wie oft und wie genau geprüft wird; der englische Schlüssel am Zeilenanfang ist Pflicht, /slice liest ihn; Standard 3, die Rundenakte kann unter „Entscheidungen“ eine andere Stufe und ihre Meilensteine festlegen, eine Slice-Datei eine eigene Stufe für diese Slice). Die Basisprüfung gilt auf jeder Stufe; „zuständige Tests“ sind die Prüfungen der kleinsten passenden Stufe (1) bis (2) oben, „Gemeinsames“ ist Stufe (2) oben plus Middleware, Datenbank-Trigger und eine neue Regel an Endpunkt, Service oder Basisklasse:
  1. Zuständige Tests ohne Scan-Tests; volle Suiten nie in der Slice; volle Prüfkette nur beim Rundenabschluss.
  2. Zuständige Tests mit Scan-Tests; bei Gemeinsamem die volle Suite des Bereichs (Desktop, API, Web); volle Prüfkette nur beim Rundenabschluss.
  3. (Standard) Wie 2; zusätzlich `-Merge -Verify` an den Meilensteinen der Rundenakte und beim Rundenabschluss, nicht nach jeder Gruppe.
  4. Wie 3; zusätzlich `-Merge -Verify` nach jeder Gruppe, und nach dem Einmischen von `dev` die vollen Suiten der Bereiche, die `dev` seit der alten Basis geändert hat.
  5. Volle Prüfkette in jeder Slice auf der Spitze und nach jedem Einmischen von `dev`; `-Merge -Verify` nach jeder Gruppe.
  Auf jeder Stufe: Nach dem Einmischen von `dev` (Schritt 6a) Basisprüfung und zuständige Tests wiederholen; volle Suiten nur, wenn die Stufe sie verlangt oder `git diff --name-only <alte Basis> dev` Dateien nennt, die auch die Slice ändert. Ein unter Last roter Test wird zuerst einzeln wiederholt, die ganze Suite nur, wenn er auch dann rot ist (als „Last, kein Fehler“ unter Überraschungen) ← Auftraggeber, 30.10.2026 (R05: die Slices 93, 104 und 118 prüften nach jedem Squash alles neu, ohne Überschneidung; die roten API-Tests von Slice 93 waren Last, einzeln und auf `dev` grün)
- Full check chain (volle Prüfkette, Rundenabschluss und slice-loop -Merge -Verify, ohne Backticks in dieser Beschriftung, denn das Skript führt jeden Text in Backticks vor dem Pfeil aus; der englische Schlüssel am Zeilenanfang ist Pflicht, das Skript liest ihn): `dotnet format AispaStudio.slnx --verify-no-changes` → `dotnet build AispaStudio.slnx -c Release` → `dotnet test --solution AispaStudio.slnx -c Release` → `cd web && npm run gen:api && npm run lint && npm run typecheck && npm test -- --maxWorkers=3 && npm run build && npm run check:bundle` ← CLAUDE.md „Befehle“, docs/arbeitsweise.md §3; `--maxWorkers=3`: Auftraggeber, 26.10.2026 (Rundenabschluss R02: ohne Begrenzung 20 Worker und Zeitüberschreitungen)

## Konflikte zwischen Dokumenten
- Push: docs/arbeitsweise.md §2 und ADR 0060 sagen „laufend auf `dev` committen und pushen“; für diese Runde gilt „nie pushen, Push nur mit Freigabe“ (Auftrag R01 und die allgemeine Freigaberegel des Auftraggebers). Nicht aufgelöst: Der Auftraggeber entscheidet, ob ADR 0060 dazu einen Nachtrag bekommt.
- Merge-Stil auf `dev`: bisher wurden Blöcke auf eigenen Branches gebaut und per Merge-Commit nach `dev` geholt („Merge T-010 …“, „Merge Runde 6 Teil 3, Block P2 …“ im git log); docs/arbeitsweise.md §4 nennt Squash nur für PRs auf `main`. Diese Runde legt je Slice einen Squash-Commit auf `dev`. Der Merge `dev` → `main` bleibt nach ADR 0060 ein Merge-Commit.
- Einsortieren im PR-Protokoll: docs/arbeitsweise.md §5 verlangt „nach PR-Nummer einsortieren“; die Abschnitte auf `dev` haben keine Nummer und stehen in Datumsfolge am Ende. Slices hängen ihren Abschnitt deshalb ans Ende.
- Nächste ADR-Nummer: CLAUDE.md nennt 0083, docs/uebergabe.md §8 noch 0068 (veraltet). Maßgeblich ist CLAUDE.md bzw. der Index docs/entscheidungen/README.md.
